## Understanding

The previous session fixed the initial slider flickering/resetting by:
1. Initializing `_last_slider_val` to match the default slider position
2. Making the "no change" branch return early without modifying parameters

However, the user reported the problem persists after the slider has been moved a few times (approximately twice). The symptoms — flickering map and slider resetting to the last value — suggest the `_last_slider_val` integer comparison was getting out of sync with the actual parameter values across ArcGIS Pro re-validation cycles.

## Root Cause Analysis

The previous fix used `_last_slider_val` (a raw integer) to compare against `int(param_slider.value)`. This comparison is fragile for two reasons:

### 1. CIM Updates Trigger Re-validation with Potentially Reset Values
When `update_or_create_layer()` modifies the map's CIM definition, ArcGIS Pro can re-evaluate the tool dialog, potentially resetting the slider parameter's value back to its default (`total_releases`). The integer comparison could not distinguish between:
- A genuine user action moving the slider to a new position
- A framework-triggered re-validation where the slider value was reset or normalized

### 2. Value Type Instability Across Validation Cycles
`param_slider.value` for a GPLong parameter can behave differently across validation cycles — sometimes returning the raw int, sometimes a Value object, sometimes being affected by internal type coercion. The raw integer comparison (`slider_val == self._last_slider_val`) was vulnerable to these inconsistencies.

### Why It Worked "Twice" Before Breaking
The initial `_last_slider_val` fix worked for the first move because the value was initialized correctly. On the second move and its subsequent re-validation cycle, the CIM update could cause ArcGIS Pro to reset the slider, creating a mismatch in the stored integer vs. actual parameter state.

## Solution

Replaced the fragile single-integer guard with a **two-layer defense**:

### Guard 1: `hasBeenValidated` Property Check (Primary)
ArcGIS Pro provides the `param.hasBeenValidated` property specifically for this purpose:
- `False` when the **user** has changed the parameter since the last validation cycle
- `True` when the parameter hasn't been touched by the user (i.e., it's a re-validation cycle)

By checking `getattr(param_slider, "hasBeenValidated", False)` first, we skip ALL re-validation cycles — regardless of what slider value ArcGIS Pro reports. This catches the CIM-update-triggered re-validation that was causing the "works twice then breaks" pattern.

### Guard 2: `_last_processed_release_id` Comparison (Secondary)
Replaced `_last_slider_val` (integer) with `_last_processed_release_id` (release ID string). Comparing by release identity instead of raw slider position is immune to:
- Value type normalization differences across validation cycles
- Slider value resets during re-validation
- Integer ↔ string coercion edge cases

## Actions Taken

### Code Changes — `WaybackImagery.pyt`

1. **Replaced `_last_slider_val` with `_last_processed_release_id`**: Tracks the release ID of the last processed update instead of a raw slider integer. Initialized to `releases[0].release_id` (newest release, matching the slider's default).

2. **Added Guard 1 — `hasBeenValidated` check**: Uses `getattr(param_slider, "hasBeenValidated", False)` to detect and skip ArcGIS Pro re-validation cycles. Falls back gracefully to `False` in test environments.

3. **Switched from `param_slider.value` to `param_slider.valueAsText`**: Uses string representation for maximum compatibility across ArcGIS Pro's internal value type handling.
